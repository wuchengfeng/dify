# Starship 老板确认版（v0.1）

更新时间：2026-04-03

这份只讲 3 件事：

1. 我们现在这套产品到底怎么串起来
2. 前端已经做到了哪一步
3. 后端下一步必须补什么

---

## 1. 现在整条业务链，已经收成什么样了

现在这套产品，已经按下面这条路收口了：

### 1.1 教练端

1. 教练登录后，不进 Dify 后台，直接进教练端
2. 教练先看到自己带的组
3. 教练进入某一个组
4. 在这个组里上课、看学生、整理自己的主版本
5. 教练发布这个组的 `main`

### 1.2 学生端

1. 学生登录后，直接进学生端
2. 学生首页只看 3 类东西：
   - 当前项目
   - 我的发布版
   - 历史项目
3. 当前项目就是课堂里的项目，只负责修改、测试、自动存版本
4. 教练发布 `main` 之后，系统会给孩子自动准备一份“我的发布版”
5. 孩子继续修改自己的“我的发布版”

### 1.3 发布与分享

1. 发布和分享已经从工作区里拆出来了
2. 现在是单独一个“发布与分享”页
3. 这个页面里只做 4 件事：
   - 写对外显示的名字
   - 写作品介绍
   - 写开场白
   - 选海报并正式发布

### 1.4 外部用户看到什么

1. 外部用户不需要登录
2. 先打开作品介绍页
3. 再进入体验页
4. 体验页是手机 H5 方向，不是后台测试页

---

## 2. 前端现在已经做到哪一步

前端现在已经不是方案稿了，而是 mock 可预览状态。

已经完成的：

1. 学生端和教练端已经彻底从 Dify 后台壳子里拆出来
2. 学生首页已经极简化
3. 教练课堂页已经按投屏课的方向收口
4. 孩子的“发布版工作区”和“发布与分享页”已经分开
5. 介绍页和体验页已经独立成外部访问页面
6. 分享海报已经是系统提前生成，不是点一下临时生成

现在你可以把它理解成：

前端主流程已经搭出来了，但现在还是 mock 数据。  
下一步最重要的是让 CTO 把真实组、真实任务、真实实时内容、真实发布数据接上。

---

## 3. 你最关心的 4 个问题，我现在怎么理解

### 3.1 孩子不能串班，教练发布了孩子就能看到

这条现在已经是正式规则：

1. 孩子同一时间不能在多个班的多个任务里同时进行
2. 组来自业务系统，不在 Starship 里临时建
3. 教练发布给某个组后，这个组里的孩子应该立刻看到

这件事不是前端自己能保证的，必须后端兜住。

### 3.2 孩子写提示词时，教练端能实时看到变化

这条现在也已经定死了：

1. 教练课堂页要能看到最多 6 个孩子当前在写什么
2. 不要求 0 延迟
3. 有几秒延时是可以接受的
4. 但不能只看历史版本，必须看到“现在正在写的内容”

### 3.3 孩子在 fork main 之后，点发布分享，有非常优质的海报

这条已经收成明确链路：

1. 教练 `main` 一旦正式发布，课堂结束
2. 系统自动给每个孩子准备一份“我的发布版”
3. 孩子进入“发布与分享”页
4. 系统提前准备 3 张海报
5. 孩子选一个喜欢的风格，正式发布

### 3.4 其他人能匿名访问孩子作品，还能给正反馈

这条现在已经明确方向：

1. 外部用户不登录也能打开孩子作品
2. 打开方式是：介绍页 -> 体验页
3. 还要加一个类似 GitHub `star` 的正反馈能力
4. 这个正反馈不一定非叫 `star`
5. 可以叫：
   - 点亮一下
   - 给个喜欢
   - 送一颗星

我建议第一阶段就先做成最简单、最稳的：

1. 不登录也能点一次
2. 有总数显示
3. 一个设备不要反复刷太多次

---

## 4. 现在给 CTO 的后端要求，已经收成什么了

最核心只有 8 件事：

1. 给出真实的教练 / 学生身份
2. 给出真实的组和组成员
3. 保证孩子不能串班、不能同时跑多个进行中的任务
4. 教练发任务后，组内孩子立刻能看到
5. 教练课堂页能看到孩子几秒内同步过来的提示词变化
6. 教练发布 `main` 后，自动给每个孩子生成一份“我的发布版”
7. 发布页支持名字、作品介绍、开场白、海报、固定二维码
8. 匿名访问作品，并支持“点赞 / 点亮 / 星标”这类正反馈

---

## 5. 现在的结论

可以把现在这件事理解成：

前端主流程已经基本串起来了。  
接下来不是再乱改方向，而是让 CTO 按这条业务骨架，把真实数据和实时能力接上。

如果 CTO 把下面这 4 条先确认下来，项目就不会跑偏：

1. 组来自业务系统
2. 孩子不能串班
3. 教练端能看到孩子实时写的提示词
4. 教练 `main` 发布后，孩子自动获得自己的发布版
